# 升级与备份

这个技能会一直改。改之前先存档，改之后能回退——否则一次冲动的重构就可能把用户几个月的记录结构搞坏。

## 一、三条铁律

1. **改之前先备份。** 没有例外，哪怕只改一个错别字。成本是几秒钟，收益是"改错了还能回去"。
2. **只加不删。** 字段、选项、记录都只增不减。删字段会清空整列数据，删选项会清空引用它的单元格，两者都不可逆。
3. **每次升级都写 CHANGELOG。** 记清楚改了什么、为什么改、怎么回退。三个月后的自己不会记得当时的判断。

## 二、版本号怎么定

`主版本.次版本.修订号`，如 `2.1.0`。

| 变化 | 版本 | 例子 |
|---|---|---|
| 只改文档措辞、修流程里的错误 | 修订号 +1 | 2.1.0 → 2.1.1 |
| 加字段、加类型选项、加新能力 | 次版本 +1 | 2.1.0 → 2.2.0 |
| 改字段语义、换存储形态、删东西 | 主版本 +1 | 2.1.0 → 3.0.0 |

**主版本升级必须先跟用户确认**，因为可能影响已有数据的含义。次版本和修订号可以直接做。

## 三、升级前备份什么

### 1. 技能文件

```bash
cd "<技能根目录>/jidou"
cp SKILL.md "archive/SKILL-v<旧版本>-$(date +%Y%m%d).md"
```

`references/` 下的文件有实质改动也一并存，命名 `references-<文件名>-v<旧版本>-<日期>.md`。

### 2. 表结构快照

```bash
python3 "<技能根目录>/library/database/get_database_schema.py" \
  --database-id "<database_id>" > "archive/schema-v<旧版本>-$(date +%Y%m%d).json"
```

结构快照比数据备份更重要——数据丢了还能从别处找，字段 ID 和选项 ID 变了就全对不上。

### 3. 数据备份

```bash
python3 "<技能根目录>/library/database/get_database_content.py" \
  --database-id "<database_id>" > "archive/data-<日期>.csv"
```

记录多的时候不必每次升级都导出，**每季度一次**或**大版本升级前**做一次就够。

### 4. 同步到资料库

本地 `archive/` 要同步到资料库 `skills/jidou/archive/`，**两边目录同名、文件名一致**。表格记录（行数、字段清单）用一个 `YYYY-MM-DD 备份说明` 的文档记，放同一个 `skills/jidou/` 目录下，不用整表搬上去。

**注意是 `archive`，不是 `_archive`。** 旧版本用过下划线开头，两种并存会有两份"历史"，其中一份永远是旧的。

**归位规则**：快照进 `archive/`，临时脚本进 `/tmp/jidou-<用途>/` 且用完删，导入导出的中间文件不进技能目录。命名、保留策略、清理周期见 `SKILL.md` 第十三节——那里是唯一口径，本文件不重复。

```bash
# 资料库建归档目录（只需一次）
python3 "<技能根目录>/library/manage/create_folder.py" \
  --title "archive" --space-id "<spaceId>" --parent-id "<jidou目录ID>"
```

## 四、改表结构时的兼容处理

### 加字段

安全。新字段必须**可空**，不能要求已有记录立刻有值。建完回读一次 `properties`，确认 ID 拿到手。

### 加选项

安全，但**必须复用已有选项的 ID**：

```json
{"id":"wdeOfSp2wBVu","text":"想法"},{"text":"新选项"}
```

不带 `id` 的是新选项，由服务端生成；带 `id` 的是已有项，ID 必须原样沿用。混错了会把老选项当新选项重建，引用它的单元格全部清空。

### 改字段类型

**不要做。** 类型一换，无法转换的单元格直接清空。真需要改，正解是新建一个字段、写脚本迁移数据、确认无误后再删旧字段——而且删旧字段这一步要单独跟用户确认。

### 改字段语义

比如「线索」从"演进编号"改成"父记录 ID"，属于主版本升级。必须：

1. 先把老数据按旧语义导出
2. 写迁移脚本转换
3. 迁移结果给用户过目
4. 确认后再改文档描述

### 改表名

慎重。技能的定位逻辑靠 `title == "记兜"` 匹配，改名会让它找不到表。要改名就同时改技能里的匹配规则，两边必须同步。

### 记兜命名升级

当前统一使用「记兜 / jidou」；旧名称只在本节用于识别已有安装，其他文档使用新名称。

| 对象 | 旧名称（仅用于兼容查找） | 当前名称 |
|---|---|---|
| 技能标识与安装目录 | `quicksave` | `jidou` |
| 展示名 | 随手记 / Quick Save | 记兜 / jidou |
| 资料库目录与表 | `速记箱` | `记兜` |
| 配置文档 | `速记箱·配置` | `记兜·配置` |
| 提醒任务 | `速记提醒` | `记兜提醒` |

首次定位的每一查都先查新名，再查表中对应的旧名。分年表与归档表按相同前缀映射，保留年份和日期后缀。配置中已有的 `database_id`、目录 ID 和 `task_id_reminder` 优先于名称；对旧 ID 回读成功就直接沿用，继续现有记录与提醒。没有有效任务 ID 时，分别按新旧任务名查重；任一命中就不创建第二个。新旧对象同时存在时，不自动合并或覆盖，按现有有效配置定位；配置也无法消歧时再询问用户。

**兼容查找不会自动改名。** 只有用户要求迁移已有安装时，才按以下顺序操作：

1. 按本文件的备份流程保存配置、表结构和任务指令；核实对象归属与 ID。
2. 对原有目录、表、配置文档及提醒任务原地更名，保留所有对象 ID、记录、字段、调度和执行参数；不重建对象，也不改记录中的用户原文。
3. 更新配置中的 `database_title`、`task_name_reminder` 和技能版本；安装目录改为 `jidou` 时同步相关路径。提醒和执行类任务中若嵌有旧标题或旧技能路径，一并更新并回读；仍使用原来的表、目录和任务 ID。
4. 用原 ID 验证记录数量、字段及任务参数未变。中断时继续兼容查找，不因部分对象已更名就重建其余对象；需要回退时按映射恢复标题与原配置、指令。

## 五、回滚

发现升级出问题时，按影响面从小到大：

| 问题 | 回滚方式 |
|---|---|
| 只是文档写错了 | 从 `archive/` 拷回上一版 `SKILL.md`，或直接改回来 |
| 加了字段但不合适 | 字段留着不动，文档里不再使用（**不删**，删了数据就没了） |
| 加了选项但不合适 | 同上，留着不用 |
| 任务频率改错了 | `scheduler-api.sh update --id <id> --cron "..."` |
| 表被改坏了 | 用 `schema-v<版本>.json` 对照恢复字段，再用 `data-<日期>.csv` 回填数据 |

**回滚成本最低的时刻永远是改之前。** 备份不是形式，是唯一能让你敢改的东西。

## 六、CHANGELOG 怎么写

在根目录 `CHANGELOG.md` 里，最新的放最上面。每条至少包含：版本号、日期、改了什么、为什么、有没有动数据。

```markdown
## 2.1.0 · 2026-11-05

**新增**
- 首次初始化流程（references/bootstrap.md）：新用户一次装好表与提醒任务
- 任务执行指令独立成文件（references/reminder-prompt.md），表 ID 用占位符

**变更**
- 建表由技能内联的 JSON 统一提供，字段顺序固定

**数据影响**
- 无。纯文档与流程调整，表结构未动
```

**「数据影响」这一栏不能空着写"无"就完事**——要么写清楚动了什么、怎么恢复，要么明确说没动。这一栏是给自己三个月后看的。

## 七、什么时候该升级

不要为了升级而升级。真正的触发点只有三个：

1. 用户提出当前能力覆盖不了的需求
2. 发现流程里确实有错，或者实测结论与文档不符
3. 平台接口变了，旧命令跑不通

日常使用中偶然想到"这样可能更好"的念头，先记进记兜（用这个技能记自己），攒到有实际痛点了再动手。
