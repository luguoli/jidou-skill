# 首次使用怎么判断

换设备、换执行环境、换 agent、换账号之后，"这是不是第一次"这个问题**不能靠本地状态回答**——本地永远是空的。

所以判断只有一条路：**先查云端，查不到才问用户，问完把答案写回云端。**

## 一、判断顺序：三查一问（严格按序，不许跳）

| # | 查什么 | 结果 | 动作 |
|---|---|---|---|
| 查1 | 配置文档「速记箱·配置」是否存在 | 在 | 读出 `database_id`，验证表还活着 → **直接用，不问** |
| 查2 | 配置文档不在，但空间里有「速记箱」表 | 在 | 接上，补一份配置文档，**不问** |
| 查3 | 都没有，但同账号下能按标题搜到 | 在别处 | 接上，**不问** |
| 问 | 三查全空 | — | **此刻才问用户** |

三查能自动答复的，绝不打扰用户。**只有真的什么都找不到，才轮到提问。**

术语就是「三查一问」，别写成"三级""四级"——两套说法在同一段里混用，曾经导致判断分歧。

## 二、怎么问

一句话，给三个选项，不解释技术细节：

> 「速记箱」还没建过。你是第一次用，还是之前有、现在找不到了？
>
> - 第一次用 → 我建好表和提醒任务
> - 之前有 → 我按标题再找一遍，或者你告诉我在哪个位置
> - 先不建 → 我只记文字，不建表

**不要问**"是否生成 csv / 是否初始化存储层"这类问题。用户不关心实现，也不该被要求做技术决定。

## 三、三种回答怎么处理

| 用户说 | 动作 |
|---|---|
| 第一次用 | 建表 → 建字段 → 建提醒任务 → 写配置文档 → **给功能清单**（`onboarding.md`） |
| 之前有 | 再搜一次全空间（不只根目录）→ 找到就接上并补配置文档；还是找不到，问是不是换了账号 |
| 先不建 | 什么都不建。之后用户再说「记一下」时，再问一次，不要默认他已经同意 |

**"先不建"之后绝不能留半个空表。** 建到一半停下，比完全没建更麻烦——下次会以为已经装过。

## 四、回答完立刻固化

用户答完，**把答案写进云端配置文档**，这是整个流程的重点：

```
init_mode = 首次使用，用户确认新建
        或 迁移，来自原空间 <原 spaceId>
        或 重建，旧表已删（用户确认）
        或 存量表，未询问（凭证于 <日期> 补写）   ← 只有表本来就存在时才用
```

**顺序是：先建表建任务，最后写凭证。** 理由不是"越快越好"，而是失败时哪一种残局更好收拾：

| 顺序 | 中途挂掉留下什么 | 下次会怎样 |
|---|---|---|
| 先建表 → 后写凭证 | 一张没有凭证的表 | 查2 命中，自动接上并补凭证。**可自愈** |
| 先写凭证 → 后建表 | 一份指向不存在表的凭证 | 查1 命中但 `node-info` 失败，判成"表没了"，可能重建。**不可自愈** |

所以 `bootstrap.md` 第六点五节写的是"最后写凭证"，本文件与它一致。任何"先写凭证再建表"的变体都是错的——空凭证比没有凭证更糟。

下次任何人、任何环境进来，读到这份文档就知道"不是第一次"，一个字都不用问。

## 五、禁止的做法

- **不要用"创建"代替"询问"。** 三查全空只说明"云端没有"，不说明"用户要建"。建表、建任务、写凭证是有后果的动作，用户没答过就不许做。这条被违反过一次：新会话里直接建好整套，用户是在看到表之后才知道的。
- **不要伪造「用户确认」。** `init_mode` 写「用户确认新建」，意味着用户真的回答过。没问就写，是把一条假授权永久存进云端，之后所有环境都会相信它，而且不会有人复核。

  也不要退而求其次写「未确认，自动创建」——那等于承认"先建后问"是允许的，只是语气委婉些。**没问就不建**；表已经存在（存量）才写「存量表，未询问」并主动告知。
- **不要用本地文件判断。** 本地目录、`~/.quicksave`、`archive/` 里的东西，在定时任务里全读不到。靠它判断必然误判。
- **不要用"探测不到"当"不存在"。** 探测失败可能是权限、网络、标题被改。先重试，再换方式查，别急着建。
- **不要建 csv 当凭证。** 云端才是唯一可信位置。
- **不要重复建。** 同名表建两张，数据就分裂了，而且没有任何报错。

## 六、重置

用户明确说「重新来一套」时：

1. 先把旧表导出（`get_database_content.py` → `archive/data-<日期>.csv`）
2. 确认用户知道旧数据不再参与提醒
3. 旧表改名，**固定格式** `速记箱-归档-YYYYMMDD`，不删。格式是固定的，因为 `SKILL.md` 第二节靠这个模式认出"这是本技能自己的旧表"；改成别的名字，下次它就成了"不认识的东西"，既不敢动也不会用
4. 建新表 → 更新配置文档的 `database_id`、`initialized_at`、`init_mode=重建`

**不删旧表。** 删了不可逆，改个名还能翻回去。
