# 记录与更新

先按 [first-run.md](first-run.md) 接回已有数据，并读取 [data-model.md](data-model.md)。需要提醒或执行时再读相应文档。

本地后端按 [local-runtime.md](local-runtime.md) 使用 add/update/complete/skip/undo；云端才使用本页的 library 接口示例。记录与原文规则相同；本地循环完成必须指定 event-at，回执和模板推进在事务内完成，不手工双写模拟事务。

## 新记与拆条

1. 确认存在记录意图；明确是随便聊天时不保存。
2. 一件独立的事一行。保留对应原始片段，内容写简述；混合输入中的秘密先去敏，见 SKILL.md。
3. 选择类型、领域与初始状态；补标签、相关人、来源。缺少非必要字段不阻止记录，不编出处。
4. 判断是否为已有线索的补充：有明确引用或唯一明显匹配时沿用；多个候选影响关联时问一句。新主题才分配新线索。
5. 日期不明确时先记录。有“提醒我”但无时间，回话问时间。已有提醒能力时，明确时间的待办/事件默认准时提醒，用户明确不提醒则关闭；其他类型不因含日期就自动提醒。调度尚未就绪时说明该时间已记下、提醒尚未启用。
6. 批量写入后回读确认每条内容、原文、线索、领域和提醒字段。部分成功只补失败项。

## 当前 library 适配器

实际路径与 CLI 能力按 [dependencies.md](dependencies.md) 检查。下列是适配器约定示例，不代表所有平台都有同名接口。
字段名对应值可用 `text/select/date` 包装；更新使用实际 `record_id`。

```json
{
  "database_id": "<database_id>",
  "records": [{
    "内容": {"text": "周报自动化：希望从聊天记录生成周报"},
    "类型": {"select": "想法"},
    "标签": {"text": "效率、自动化"},
    "线索": {"text": "Q20261106-01"},
    "记录时间": {"date": "2026-11-06"},
    "状态": {"select": "待看"},
    "提醒": {"select": "不提醒"},
    "领域": {"select": "工作"},
    "原文": {"text": "周报能不能自动从聊天记录里长出来"}
  }]
}
```

先用 JSON 序列化把实际请求写入本次独立临时目录，再调用接口；不要把用户原话拼进 shell 字符串、`printf`、`sed` 或命令替换。

```bash
python3 "$LIB/database/batch_add_database_records.py" --stdin < "$JIDOU_TMP/records.json"
```

超时、断连或部分失败时，先按返回 ID、线索、原文和记录时间查询结果。适配器支持幂等键时使用它；不支持时，核对清楚再重试，无法消歧就报告结果未知。相同原话在不同时间也可能是用户确实再次记录，不能仅凭文本相同删除。

## 更新

定位到唯一记录后，只提交需变化的字段；与用户指代有歧义时列出少量候选。

| 请求 | 更新与联动 |
|---|---|
| 补充一个旧想法 | 新增一行、复用线索；不覆盖原文或其他记录状态 |
| 这条记错了 | 更新已定位记录的内容/结构字段；原文仍保留当时输入，不把纠正后的话伪装成旧原话 |
| 完成这个一次性待办 | 状态=已完成，完成于=用户时区今天 |
| 这个不做了 | 状态=归档；有关联独立任务时先停用相应任务再回读 |
| 循环任务这次做完了 | 按下方本期完成流程登记、抑制该期提醒；循环模板保持有效 |
| 整个循环结束了 | 明确是结束整个系列才归档模板，独立执行任务也相应停用 |
| 变成不需提醒的想法 | 清除到期、下次触发、静音和重复；提醒=不提醒；有关联任务时先说明并停用 |
| 改标签、领域、相关人 | 只改该字段；文本追加先读原值后合并 |
| 时间、提前量、静音、单次改期 | 按 [reminders.md](reminders.md)，不套统一“两个时间都改”规则 |
| 撤销误打卡、误跳过 | 按下方撤销流程，将指定回执作废，核对是否需要恢复该期提醒 |

清空字段的 `null`/空对象/空字符串约定依适配器确认，不盲猜。任何删除都需要用户明确要求，普通完成、整理、归档不删除记录。
写完核对目标记录 ID 与字段；一句话告诉用户当前状态。未成功持久保存时不能回“记好了”。

## 循环本期完成

1. 定位循环模板和用户完成的具体事件时刻。提前提醒后下次触发可能已经滚到下月，因此同时检查模板最近的 event_at、当前下次触发和用户指代；有多个可能的期次就问日期，不直接认为完成的是最新下次触发。
2. 新增一条已完成记录，沿用线索、保存真实打卡原话，在该完成记录的上次结果写 JSON：`{"kind":"completion","status":"completed","template_database_id":"<模板database_id>","template_record_id":"<模板record_id>","event_at":"<已完成期次ISO时刻>"}`。完成于是实际完成日期，记录时间是补记日期。
3. 模板仍保持有效。在其上次结果写 `{"kind":"occurrence","event_at":"<已完成期次ISO时刻>","status":"completed"}`。若模板下次触发仍指向该期，按原规则推进；若已因提前提醒滚到了更晚一期，就保持那个更晚值，不再多跳一期。
4. 回读完成记录和模板。两次写入不是事务；只完成子记录而模板更新失败时报告部分成功，保留显式期次回执供后台核对后抑制同一期，不盲目重复添加完成记录。其他同线索记录不变。

## 撤销误打卡或误跳过

1. 定位具体模板 ID、期次及用户要撤销的回执。多条同日记录、跨表同名或历史期次不明确时先核对，不按线索整组撤销。
2. 将该子记录回执中的 status 改为 voided、记录状态改为归档，保留原文、原期次和事实历史。已有 voided 回执不再重复撤销。旧版仅有模板 occurrence 标记时，须确认它仍对应目标期次，不覆盖后来的其他标记。
3. 同期没有其他有效完成/跳过证据时，才考虑恢复该期。模板当前标记若正是被撤销期次，则使该标记失效；若对应更晚的期次则保持不动。撤销统计不等于抹掉真实已发送通知。
4. 原提醒尚未到且没有更晚已处理期次时，可恢复该期下次触发；已过去时说明可补一次提醒或只恢复未完成，按用户选择处理，不偷偷补发。若回退会覆盖更晚已生成/完成的期次，不回退系列，按实际需要单独恢复该期的待办/一次性提醒。
5. 回读回执与模板；只完成部分更新时说明状态并保留恢复线索，不声称整套已撤销。后台必须忽略 voided 回执，复盘和连续打卡统计排除这些记录。
