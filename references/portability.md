# 运行环境与移植

这个技能不绑定某一个平台。它依赖的是**三类能力**，不是一个产品名。

当前实现跑在 WorkBuddy 上，但原因只是"第一个装好的环境在那儿"。换到别的 agent 平台、换一套自建服务，只要把三类能力对上，逻辑一行都不用改。

## 一、它到底依赖什么

| 能力 | 作用 | 当前实现 | 缺了会怎样 |
|---|---|---|---|
| **内容存储** | 存记录、查记录、改记录；要能按条件筛 | 资料库（一张表 + 字段），脚本在 `library` 技能下 | 完全不可用，没有替代方案，这是地基 |
| **调度** | 按 cron 叫醒一个任务 | 自动化任务服务，`scheduler-api.sh` | 提醒失效，但**记录功能照常**——可以先只记不提醒 |
| **执行环境** | 任务被叫醒后跑代码 | 平台提供的隔离执行环境（独立于对话，Python + 网络） | 只能推文本，不能跑脚本调 API |

功能受影响的顺序是：内容存储 > 调度 > 执行环境。**只要内容存储能用，这个技能就有价值**；另外两个是加分项。

## 二、当前实现的位置

```
<技能根目录>/library/                     内容存储
├── space_api.py                          空间、节点查询
├── database/                             表的增删改查、字段管理
└── doc/                                  文档创建（整理稿用）

<技能根目录>/automation-task-manager/     调度
└── scripts/scheduler-api.sh              create / update / get / list / delete
```

`<技能根目录>` 的默认值是 `~/.codebuddy/skills`。文档里凡是出现这个路径，都是**默认值不是硬性要求**——实际位置以运行时注入的环境变量为准，取不到再退回默认值。

文档中的写法：

```bash
SKILLS="${CODEBUDDY_SKILL_DIR:-$HOME/.codebuddy/skills}"   # 技能根目录
LIB="$SKILLS/library"                                      # 内容存储
ATM="$SKILLS/automation-task-manager"                      # 调度
```

**变量名带 `CODEBUDDY_` 只说明当前是谁在注入，不代表只能在那个环境跑。** 换平台时把变量名换掉，或者直接改这两行的默认值，其余不动。

## 三、移植到别的平台

按顺序做，每步都能单独验收：

### 步骤 1 · 内容存储（必须）

新平台要能提供：建表、加字段、按条件查记录、批量增改、按 ID 删。

对照 `library` 技能的脚本清单，一个接口一个接口地对：能对上就直接用，对不上写个同名的薄封装，让 `bootstrap.md` 里的命令保持不变。

**表结构不用重新设计**，21 个字段照搬，见 `bootstrap.md` 第四节那份建表 JSON。

### 步骤 2 · 调度（强烈建议）

需要：cron 表达式、时区、启停、查询下次运行时间、能带一段文本指令。

`reminder-prompt.md` 是纯文本，跟调度接口无关——只要新平台能定时把这段文本交给一个会执行任务的 agent，提醒就能工作。

Cron 用六段（秒 分 时 日 月 周），`0 0 * * * *` = 每小时整点。如果新平台只支持五段，去掉秒位即可。

### 步骤 3 · 执行环境（可选）

需要：Python 3、HTTP 出网、能读技能目录下的脚本。

**不支持也没关系**：把「执行」字段的选项从「脚本/API/组合」收窄到「仅提醒」，其余功能不受影响。

## 四、数据搬家

技能本身可以换，**数据不能丢**。迁移只有两条路：

| 方式 | 怎么做 | 适用 |
|---|---|---|
| 导出再导入 | `get_database_content.py` 出 CSV，新平台建同结构表后批量写回 | 记录少于几千条，一次性迁移 |
| 双写过渡 | 新旧各写一份，跑一段时间核对无误再切 | 不想中断使用 |

**迁移前必须做一次完整导出并校验行数**，导出文件留在 `archive/data-<yyyymmdd>.csv`。校验方法：导出后数行数，与 `query_database_record.py` 返回的条数比对，一致才算成功。

字段 ID 会变，字段**名称**不变。所以别在任何文档里存 ID：迁移后第一件事是跑一次 `get_database_schema.py` 确认 21 个字段都在、名称没变。旧的 ID 一个都用不了，也不用去找。

## 五、判断"是不是被绑定死了"

一个简单的测试：把文档里所有 `WorkBuddy`、`codebuddy`、`workbuddy.cn` 换成占位符，读一遍还通不通顺。

如果某段话在替换后讲不通，说明那段把**产品特性当成了逻辑前提**，需要重写成能力描述。比如：

- ❌「WorkBuddy 资料库的表格不支持 title 列，所以第一列是内容」
- ✅「存储层不保证自带 title 列，所以第一列就是内容」

前者换个平台就失效，后者是通用约束。

## 六、已知的平台相关点（换环境时逐个核对）

| 位置 | 内容 | 处理 |
|---|---|---|
| `SKILL.md` 第三节 | 脚本路径变量 | 改默认值即可 |
| `SKILL.md` 第七节 | 调度命令 `scheduler-api.sh` | 换平台重写封装，参数保持同名 |
| `SKILL.md` 零节「装好之后」 | 表格访问链接 `<表格访问地址>` | 占位符，运行时从 `node-info` 的 `url` 取 |
| `references/reminder-prompt.md` | 脚本绝对路径 | 建任务时用 `sed` 替换成新路径 |
| `references/bootstrap.md` | 三类路径变量 | 文件开头三行 |
| `references/dependencies.md` 第三节 | 五个实例值的取法 | 换环境后值全变，取法不变；不要往里填新 id |

除以上六处，其余内容与平台无关。改完按 `consistency.md` 跑一遍交叉引用检查——节号最容易因为加一节而集体错位。
