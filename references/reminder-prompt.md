扫描用户的记兜，推送此刻该提醒的事项。

【输出契约·最高优先级，压过下面所有内容】
你的输出会原样发给用户，所以只输出用户该看到的东西。

- 有提醒 → 每条一行，格式：`<时间> <内容> [领域]`。不写开头结尾，不解释为什么推、不写检查区间、不说「扫描完成」。
- 没有提醒 → **一个字符都不要输出**。不写「暂无提醒」，不写「本时段无需推送」，不复述判断过程。
- 禁止出现在输出里的词：检查区间、扫描、未完成记录、静默时段、提醒时刻、本条规则本身。
- 内部判断（时间比较、静音过滤、逾期标注）全部在你自己脑子里完成，写出来就是错的。

下面所有章节是给你执行的步骤，不是给用户看的文字。
过程中不要发任何中间消息，全部判断做完后一次性输出。

数据源：资料库表格 database_id=__DATABASE_ID__（表名「记兜」）
字段：内容、类型、标签、线索、记录时间、状态、到期、提醒、重复、下次触发、静音至、完成于、执行、执行内容、任务ID、上次结果、领域、优先级、相关人、来源、原文
（共 21 个。推送只用到内容/领域/到期/下次触发/提醒/静音至/状态/重复这几列，其余照常读出来放着，不要因为用不上就当成不存在。**「原文」永远不要出现在推送里**——那是留给用户自己回看的原话，长的能有几百字，混进来会把一行一条的格式撑爆。）

【执行环境须知】
本次运行在一个独立的临时执行环境里，和用户对话时那个环境**不是同一个**：看不到对话里的任何文件，读不到技能目录里的 archive，上一次执行留下的文件也未必还在。

因此有一条铁律：

> **「记兜」是一张云端表格，不是本地文件。这个环境里没有 xlsx、没有 csv、没有任何记兜文件，这是正常的，不是出问题了。**

数据只有一处：通过 library 脚本读写的云端表格 `database_id=__DATABASE_ID__`。

**绝对禁止的行为**，任何一条都算严重错误：

- 找不到表就本地新建 csv / xlsx / json / sqlite 来"兜底"
- 把数据写到 /tmp、/workspace、当前目录或任何本地路径
- 自己建表、加字段、改结构
- 用 curl 或脚本直连数据库、绕过 library 接口

本地兜底最危险：它让任务看起来"成功"了，用户却永远收不到提醒，而且没人会发现。宁可失败留痕，也不要假成功。

只依赖两样东西：library 技能的官方脚本、云端表格接口。脚本路径一律用绝对路径（建任务时已替换成该环境的真实路径），不要用 $HOME 或相对路径。

步骤 0　前置自检（不可跳过）
先确认表能读：
cd __SKILLS_DIR__/library/database && python3 query_database_record.py --database-id __DATABASE_ID__
读失败（表不存在、无权限、接口报错）→ **立即结束**。

结束前只做一件事：重试一次（网络抖动是常见的）。仍失败就停，**不建表、不建文件、不建任务、不改结构、不换数据源**。

后台任务建错了没人拦：第二天会多出几张空表，或者多出一堆 csv，而用户以为一切正常。失败要留痕（往「上次结果」写一行，写不了就静默退出），但绝不用本地数据顶上。

步骤 0.5　夜间静默
看当前北京时间。若在 22:00–08:00 之间，**直接结束，不推送任何内容**。
若当前是 08 点这一场，把检查区间设为「昨晚 22:00 到现在」，用来补推夜间错过的事项；其余时段检查区间为「当前整点到现在」。

步骤 1　取未完成记录
cd __SKILLS_DIR__/library/database && python3 query_database_record.py --database-id __DATABASE_ID__ --filter '{"and":[{"property":{"property":"状态","select":{"does_not_equal":"已完成"}}},{"property":{"property":"状态","select":{"does_not_equal":"归档"}}}]}'

步骤 2　逐条计算
触发点 = 「下次触发」有值就用它，为空则退回用「到期」；两者都空则跳过（这类是没时间的待办，不提醒）。
若「静音至」有值且晚于现在 → 整条跳过，不做任何计算。
提醒时刻 = 触发点 − 提前量。
提前量：不提醒→跳过；准时→0；提前10分钟→10分钟；提前1小时→1小时；提前1天→24小时；提前3天→72小时；提前1周→168小时。
提醒时刻落在步骤 0.5 确定的检查区间内 → 列入本次推送。

逾期 = 触发点早于现在，且状态不是已完成/归档。逾期项**不会因为逾期而额外进入本次推送**——它的提醒时刻已经过去，只有恰好落在区间里才算命中。不要把逾期当成"该推"的理由，否则一条没做的待办会每小时响一次。

步骤 3　合并
同一「线索」编号有多条命中时，合并成一条推送：写一句共同主题，下面列各子项，不要一条一条刷屏。不同线索之间分开写。

步骤 4　推送格式
严格照开头的输出契约，一条一行：

```
19:30  把合同发给老张  [工作]
明天 09:00  交房租  [生活]
```

- 时间取「下次触发」的时分。今天的只写时分，不是今天的写「11-08 09:00」
- 领域用方括号跟在最后，没有就省略
- **本条命中且已逾期**的，行末加「（已逾期 N 天）」
- 本批已有推送时，若全表还有逾期未完成、但本批没命中的，最后单独一行：「另有 N 项逾期」。**本批没有任何命中时，这一行也不写**，直接空输出
- 同一线索合并时，第一行写主题，下面两空格缩进列子项

**除了这几行，不要再多写一个字。** 不写标题、不写总结、不写「以上」、不问「需要我帮你标记完成吗」。

步骤 5　滚动更新
循环任务（重复字段非空）推送后，**按「重复」规则重新计算下一次**，不要在当前「下次触发」上简单加一个周期——用户可能手动改过这一期，叠加会越漂越远。
cd __SKILLS_DIR__/library/database && python3 batch_update_database_records.py --database-id __DATABASE_ID__ --records '[{"record_id":"<记录ID>","properties":{"下次触发":{"date":"<下一周期ISO时间>"}}}]'

农历换算用 lunardate（执行环境已带）：
python3 -c "from lunardate import LunarDate; import datetime; t=datetime.date.today(); print(next(d for d in (LunarDate(y,3,28).toSolarDate() for y in range(t.year,t.year+3)) if d>t))"
年份和月日按「重复」字段的实际值替换。每年公历落点都不同，必须逐年重算。

约束
只更新「下次触发」。不要改「到期」「重复」「内容」「状态」「静音至」「完成于」。
不要新建表，不要创建或修改定时任务。
不要往本地写任何文件；需要留痕就写回表格字段。
用户说「静音」「别提醒了」这类话时要改的是「静音至」，不是删除记录——这个判断发生在对话里，不发生在本次扫描里。
脚本报错就用一句话说清哪一步失败，不要贴原始 JSON、堆栈或内部 ID。
